## 一、项目背景与业务目标

### 1.1 背景

企业内部有大量沉淀在文档（如 Markdown）中的知识（制度、流程、FAQ），但员工查找困难。本项目构建一个**企业微信智能机器人（AIBot）本地知识库应答系统**，让员工在企业微信中 @ 机器人提问，机器人从本地知识库检索并自动回复。

### 1.2 业务目标

| 目标     | 说明                                |
| ------ | --------------------------------- |
| 群聊触发应答 | 群内用户 @ 本机器人（或 @ 配置的指定人）时进入回复流程    |
| 多消息聚合  | 同一用户在时间窗（默认 30 秒）内的连续消息聚合为完整问题    |
| 单聊直答   | 单聊中用户发消息即视为新问题，直接检索回复             |
| 纯本地检索  | 默认不调用大模型，SQLite FTS5 全文检索即回复      |
| 无结果记录  | 检索不到或低置信度时，不转人工，写入"待补充问题表"并返回温和话术 |
| 可视化运维  | Web 界面管理知识库、查看待补充问题、配置系统参数        |

***

## 二、核心业务规则说明

1. **群聊聚合规则**（核心）：

   - 仅当首条消息 @ 本机器人（或 @ 指定人）时，才开始聚合该 `chatid + userid` 的缓冲区；

   - 同一 `userid` 在时间窗内的连续消息拼接为完整问题；

   - 时间窗内其他 `userid` 的发言**不中断**当前用户的聚合计时（仅忽略）；

   - 时间窗到期后触发检索；若首条消息未 @ 本机器人，整个缓冲丢弃。

2. **单聊规则**：用户发消息即视为新问题，不聚合，直接检索回复。

3. **回复格式**：每条回复前拼接可配置前缀，默认 `[AI自动回复]：`。

4. **无结果处理**：检索不到或置信度低于阈值时，不转人工，将原始问题写入待补充问题表，返回温和的无结果话术。

5. **消息排重**：基于企微回调 `body.msgid` 做排重，防止网络重试导致重复处理。

6. **并发限制**：用户跟同一个智能机器人最多同时有 3 条消息交互中（企微硬限制），需做队列控制。

## 三、技术选型依据

| 选型                   | 理由                                         |
| -------------------- | ------------------------------------------ |
| Python 3.11+         | 生态成熟、异步支持好、开发效率高                           |
| FastAPI              | 异步高性能、原生支持 async/await、自动校验请求、适合长连接回调服务    |
| SQLite (FTS5)        | 纯本地部署零依赖、单文件免运维、FTS5 提供全文检索能力，满足轻量级 RAG 需求 |
| Jinja2 + Bootstrap 5 | 轻量模板渲染 + 现成 UI 组件，快速搭建 Web 管理界面            |
| httpx                | 异步 HTTP 客户端，用于企微被动回复 / 主动推送                |
| pyyaml               | 配置文件 `config.yaml` 解析                      |

> **为什么不调大模型**：项目定位为纯本地、低成本、隐私安全的轻量级系统。知识库以内部文档为主，FTS5 关键词检索即可覆盖大部分 FAQ 场景，无需大模型推理成本。检索阈值不满足时走"待补充问题"记录闭环，由管理员补充知识。

**依赖清单（requirements.txt）**：仅 `fastapi`、`uvicorn`、`httpx`、`pyyaml`、`jinja2`。

### 4.2 数据流

```
消息回调 → msgid 排重 → chattype 分流
  ├─ single → 直接检索 → 有结果(前缀+回复) / 无结果(记录待补充+温和话术)
  └─ group  → chatid+userid 缓冲聚合 → 时间窗到期 → 首条未@丢弃 / 已@则检索 → 回复
```

## 六、风险点与约束

| 风险 / 约束      | 说明                         | 应对措施                            |
| ------------ | -------------------------- | ------------------------------- |
| 企微 3 条消息并发限制 | 用户与同一机器人最多同时 3 条消息交互中      | 实现消息队列控制，串行/受限并发处理              |
| 群聊 @ 强提醒不可用  | 企微原生智能机器人默认不支持真正的 @ 强提醒    | 回复开头加 "@提问人" 文本前缀变通             |
| 消息重复回调       | 网络原因可能重复推送同一 msgid         | 基于 `msgid` 去重                   |
| userid 可能加密  | 非超级管理员创建者时 userid 为加密值     | 以 `from.userid` 原始值参与聚合/去重，不做假设 |
| 被动回复类型受限     | `response_url` 部分场景返回且类型受限 | 以官方最新文档为准，必要时回退主动推送             |
| 长连接明文回调      | 长连接模式回调为明文，无需解密            | 无需加解密处理，但需解析固定报文结构              |
| 检索精度有限       | FTS5 关键词检索可能误判/漏判          | 设置信度阈值 + 待补充问题记录闭环              |
| SQLite 并发写   | 高并发下写锁                     | 单实例部署 + 事务控制，避免长事务              |

## 八、验收标准（整体）

1. 群聊中 @ 机器人，30 秒内连续消息可聚合为完整问题并正确回复；
2. 单聊发消息直接回复；
3. 检索不到时写入待补充问题表并返回温和话术，不转人工；
4. Web 界面可管理知识库、查看待补充问题、配置系统参数；
5. 全流程基于 `msgid` 排重，无重复处理；
6. 代码符合代码规范（中文注释、参数化 SQL、try/except、单函数 ≤50 行）。
